# 撰寫計畫

## 概覽

撰寫完整的實作計畫，假設執行的工程師對我們的程式碼庫零了解、品味存疑。記錄他們需要知道的一切：每個任務要動哪些檔案、程式碼、測試、可能需要查閱的文件、如何測試。把完整計畫拆成一口一口可以消化的任務。DRY。YAGNI。TDD。頻繁提交。

假設對方是有能力的開發者，但對我們的工具集或問題領域幾乎一無所知。假設他們不太懂好的測試設計。

**開始時宣告：**「我正在使用 writing-plans skill 來建立實作計畫。」

**背景：** 若在隔離的 worktree 中工作，應已在執行時透過 `superpowers:using-git-worktrees` skill 建立。

**計畫儲存至：** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- （使用者對計畫位置的偏好設定會覆蓋此預設值）

## 範疇確認

若規格涵蓋多個獨立子系統，應已在腦力激盪期間拆分為子專案規格。若尚未拆分，建議拆成各自獨立的計畫——每個子系統一份。每份計畫應能各自產生可運作、可測試的軟體。

## 檔案結構

在定義任務之前，先梳理哪些檔案將被建立或修改，以及各自負責什麼。這是鎖定分解決策的關鍵環節。

- 設計邊界清晰、介面定義明確的單元。每個檔案應有單一明確的職責。
- 你能一次納入 context 的程式碼，推理最可靠；聚焦的檔案讓你的編輯更準確。優先使用小而聚焦的檔案，而非做太多事的大檔案。
- 一起變動的檔案應放在一起。按職責分割，而非按技術層次分割。
- 在既有程式碼庫中，遵循已建立的模式。若程式碼庫使用大型檔案，不要擅自重組——但若你正在修改的檔案已過於龐大，在計畫中納入拆分是合理的。

此結構決定任務分解方式。每個任務應產生獨立有意義的自包含變更。

## 一口一口的任務粒度

**每個步驟是一個動作（2–5 分鐘）：**
- 「撰寫失敗的測試」—— 一個步驟
- 「執行它以確認它失敗」—— 一個步驟
- 「實作讓測試通過的最小程式碼」—— 一個步驟
- 「執行測試並確認它們通過」—— 一個步驟
- 「提交」—— 一個步驟

## 計畫文件標頭

**每份計畫必須以此標頭開始：**

```markdown
# [功能名稱] 實作計畫

> **給代理工作者：** 必要子技能：使用 superpowers:subagent-driven-development（推薦）或 superpowers:executing-plans 來逐任務實作此計畫。步驟使用核取方塊（`- [ ]`）語法進行追蹤。

**目標：** [一句話描述這個計畫要建構什麼]

**架構：** [2–3 句話說明方法]

**技術棧：** [關鍵技術/函式庫]

---
```

## 任務結構

````markdown
### 任務 N：[元件名稱]

**檔案：**
- 建立：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 測試：`tests/exact/path/to/test.py`

- [ ] **步驟 1：撰寫失敗的測試**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步驟 2：執行測試以確認它失敗**

執行：`pytest tests/path/test.py::test_name -v`
預期：FAIL，訊息為「function not defined」

- [ ] **步驟 3：撰寫最小實作**

```python
def function(input):
    return expected
```

- [ ] **步驟 4：執行測試以確認它通過**

執行：`pytest tests/path/test.py::test_name -v`
預期：PASS

- [ ] **步驟 5：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 禁止佔位符

每個步驟必須包含工程師實際需要的內容。以下是**計畫失敗**的表現——絕對不要寫：
- 「TBD」、「TODO」、「稍後實作」、「填入細節」
- 「加入適當的錯誤處理」/「加入驗證」/「處理邊界情況」
- 「為上述內容撰寫測試」（沒有實際測試程式碼）
- 「類似任務 N」（重複那段程式碼——工程師可能不按順序閱讀任務）
- 描述要做什麼卻不展示如何做的步驟（程式碼步驟必須附程式碼區塊）
- 參照任何任務中未定義的型別、函式或方法

## 重要提醒
- 永遠使用精確的檔案路徑
- 每個步驟都要有完整程式碼——若步驟更動程式碼，就展示程式碼
- 精確的指令及其預期輸出
- DRY、YAGNI、TDD、頻繁提交

## 自我審查

撰寫完整計畫後，用全新的眼光對照規格檢查計畫。這是你自己執行的核對清單——不是派遣子代理。

**1. 規格覆蓋：** 瀏覽規格中的每個段落/需求。你能指出哪個任務實作了它嗎？列出任何缺口。

**2. 佔位符掃描：** 在計畫中搜尋紅旗——「禁止佔位符」段落中的任何模式。修正它們。

**3. 型別一致性：** 你在後期任務中使用的型別、方法簽章和屬性名稱，是否與你在前期任務中定義的相符？在任務 3 中叫做 `clearLayers()` 但在任務 7 中叫做 `clearFullLayers()` 就是一個 bug。

若發現問題，就地修正。無需重新審查——修正後繼續前進。若發現規格需求沒有對應任務，就補上該任務。

## 交接執行

儲存計畫後，提供執行方式選擇：

**「計畫已完成並儲存至 `docs/superpowers/plans/<filename>.md`。兩種執行選項：**

**1. 子代理驅動（推薦）** — 我為每個任務派遣一個全新子代理，任務間進行審查，快速迭代

**2. 內聯執行** — 在本次會話中使用 executing-plans 執行任務，分批執行並設有檢查點

**選擇哪種方式？」**

**若選擇子代理驅動：**
- **必要子技能：** 使用 superpowers:subagent-driven-development
- 每個任務一個全新子代理 + 兩階段審查

**若選擇內聯執行：**
- **必要子技能：** 使用 superpowers:executing-plans
- 分批執行並設有檢查點進行審查
