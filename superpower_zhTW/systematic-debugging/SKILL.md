# 系統化除錯

## 概觀

隨機嘗試修復會浪費時間並製造新的錯誤。快速補丁會掩蓋根本問題。

**核心原則：** 在嘗試任何修復之前，務必先找出根本原因。修復症狀即是失敗。

**違反此流程的文字，就是違反除錯的精神。**

## 鐵律

```
未完成根本原因調查之前，不得提出任何修復方案
```

若尚未完成第一階段，不得提出修復方案。

## 使用時機

適用於任何技術問題：
- 測試失敗
- 生產環境錯誤
- 非預期行為
- 效能問題
- 建置失敗
- 整合問題

**尤其在以下情況下務必使用：**
- 面臨時間壓力（緊急情況使人傾向猜測）
- 「只是一個快速修復」看似顯而易見
- 已嘗試多次修復
- 先前的修復無效
- 尚未完全理解問題

**以下情況不得跳過：**
- 問題看似簡單（簡單的錯誤也有根本原因）
- 趕時間（倉促只會保證需要返工）
- 主管要求立刻修好（系統化比反覆嘗試更快）

## 四個階段

必須完成每個階段後，才能進行下一個階段。

### 第一階段：根本原因調查

**在嘗試任何修復之前：**

1. **仔細閱讀錯誤訊息**
   - 不要略過錯誤或警告
   - 訊息中通常包含確切的解決方案
   - 完整閱讀 stack trace
   - 記下行號、檔案路徑、錯誤代碼

2. **穩定重現**
   - 能否可靠地觸發問題？
   - 確切步驟為何？
   - 是否每次都發生？
   - 若無法重現 → 蒐集更多資料，不要猜測

3. **檢查近期變更**
   - 哪些變更可能造成此問題？
   - git diff、近期 commit
   - 新增的相依套件、設定變更
   - 環境差異

4. **在多元件系統中蒐集證據**

   **當系統包含多個元件（CI → 建置 → 簽署、API → 服務 → 資料庫）時：**

   **在提出修復方案之前，先加入診斷性埋點：**
   ```
   對每個元件邊界：
     - 記錄進入元件的資料
     - 記錄離開元件的資料
     - 驗證環境/設定的傳遞
     - 在每一層檢查狀態

   執行一次以蒐集能顯示哪裡出錯的證據
   再分析證據以找出失敗的元件
   再調查該特定元件
   ```

   **範例（多層系統）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **此方式揭露：** 哪一層失敗（secrets → workflow ✓、workflow → build ✗）

5. **追蹤資料流**

   **當錯誤位於 call stack 深處時：**

   完整的向後追蹤技術，請參見本目錄中的 `root-cause-tracing.md`。

   **快速版本：**
   - 錯誤值從何而來？
   - 哪個呼叫者傳入了錯誤值？
   - 持續向上追蹤直到找到來源
   - 在來源處修復，而非在症狀處修復

### 第二階段：模式分析

**修復之前先找出模式：**

1. **尋找可用範例**
   - 在同一個程式碼庫中尋找類似的可用程式碼
   - 哪些可用的程式碼與出問題的相似？

2. **對照參考資料**
   - 若要實作某個模式，請完整閱讀參考實作
   - 不要略讀——逐行閱讀
   - 充分理解模式後再套用

3. **找出差異**
   - 可用的與出問題的有何不同？
   - 列出所有差異，無論多細微
   - 不要假設「那個不可能有影響」

4. **理解相依關係**
   - 這個元件還需要哪些其他元件？
   - 需要哪些設定、組態、環境？
   - 它做了哪些假設？

### 第三階段：假說與測試

**科學方法：**

1. **形成單一假說**
   - 清楚陳述：「我認為 X 是根本原因，因為 Y」
   - 將其寫下來
   - 要具體，不要模糊

2. **最小化測試**
   - 做出最小幅度的變更來測試假說
   - 每次只改變一個變數
   - 不要同時修復多件事

3. **繼續前確認結果**
   - 有效了嗎？有 → 進入第四階段
   - 無效？形成新的假說
   - 不要在上面再疊加更多修復

4. **當你不知道時**
   - 說「我不理解 X」
   - 不要假裝知道
   - 尋求協助
   - 進行更多研究

### 第四階段：實作

**修復根本原因，而非症狀：**

1. **建立失敗測試案例**
   - 最簡單可能的重現方式
   - 若有測試框架，建立自動化測試
   - 若無框架，建立一次性測試腳本
   - 修復前必須先有測試
   - 使用 `superpowers:test-driven-development` skill 來撰寫正確的失敗測試

2. **實作單一修復**
   - 針對已找出的根本原因
   - 每次只做一個變更
   - 不要「順手」做改進
   - 不要捆綁重構

3. **驗證修復**
   - 測試現在通過了嗎？
   - 沒有其他測試被破壞嗎？
   - 問題確實解決了嗎？

4. **若修復無效**
   - 停止
   - 計算：已嘗試幾次修復？
   - 若少於 3 次：帶著新資訊回到第一階段重新分析
   - **若達到 3 次以上：停止並質疑架構（見下方步驟五）**
   - 不得在未進行架構討論的情況下嘗試第四次修復

5. **若 3 次以上修復失敗：質疑架構**

   **指示架構問題的模式：**
   - 每次修復都揭露出不同地方的新共用狀態/耦合/問題
   - 修復需要「大規模重構」才能實作
   - 每次修復都在其他地方製造新的症狀

   **停止並質疑根本：**
   - 這個模式根本上是否可行？
   - 我們是否「只是因為慣性而堅持下去」？
   - 應該重構架構，還是繼續修復症狀？

   **在嘗試更多修復之前，先與你的人類夥伴討論**

   這不是假說失敗——這是錯誤的架構。

## 紅旗——停止並遵循流程

若你發現自己正在想：
- 「先快速修復，之後再調查」
- 「試著改 X 看看有沒有用」
- 「加入多個變更，執行測試」
- 「跳過測試，我手動驗證就好」
- 「可能是 X，讓我先修那個」
- 「我不完全理解，但這或許有用」
- 「模式說 X，但我會用不同的方式調整」
- 「以下是主要問題：[列出修復方案而未先調查]」
- 在追蹤資料流之前就提出解決方案
- **「再試一次修復」（已嘗試 2 次以上時）**
- **每次修復都揭露出不同地方的新問題**

**以上全部意味著：停止。回到第一階段。**

**若 3 次以上修復失敗：** 質疑架構（見第四階段步驟五）

## 你的人類夥伴發出你做錯了的信號

**留意這些重新導引：**
- 「那不是正在發生嗎？」——你在未驗證的情況下做了假設
- 「它會讓我們看到……嗎？」——你應該加入證據蒐集
- 「停止猜測」——你在未理解的情況下提出修復方案
- 「對這個進行 ultrathink」——質疑根本，而非只是症狀
- 「我們卡住了嗎？」（沮喪）——你的方法不起作用

**看到這些時：** 停止。回到第一階段。

## 常見的合理化藉口

| 藉口 | 現實 |
|--------|---------|
| 「問題很簡單，不需要流程」 | 簡單的問題也有根本原因。流程對簡單錯誤而言同樣快速。 |
| 「緊急，沒時間走流程」 | 系統化除錯比猜測嘗試更快。 |
| 「先試這個，之後再調查」 | 第一次修復奠定了模式。從一開始就做對。 |
| 「確認修復有效後再寫測試」 | 未經測試的修復不會持久。先寫測試能加以證明。 |
| 「一次做多個修復節省時間」 | 無法分離哪個有效。會製造新的錯誤。 |
| 「參考資料太長，我自己調整模式」 | 片面理解保證會有錯誤。完整閱讀它。 |
| 「我看到問題了，讓我修它」 | 看到症狀 ≠ 理解根本原因。 |
| 「再試一次修復」（2 次以上失敗後） | 3 次以上失敗 = 架構問題。質疑模式，不要再修了。 |

## 快速參考

| 階段 | 主要活動 | 成功標準 |
|-------|---------------|------------------|
| **1. 根本原因** | 閱讀錯誤、重現、檢查變更、蒐集證據 | 理解「什麼」與「為什麼」 |
| **2. 模式** | 尋找可用範例、比較 | 找出差異 |
| **3. 假說** | 形成理論、最小化測試 | 確認或形成新假說 |
| **4. 實作** | 建立測試、修復、驗證 | 錯誤已解決，測試通過 |

## 當流程揭露「無根本原因」時

若系統化調查揭露問題確實是環境性、依賴時間或外部因素造成的：

1. 你已完成流程
2. 記錄你所調查的內容
3. 實作適當的處理（重試、逾時、錯誤訊息）
4. 加入監控/記錄以利未來調查

**但：** 95% 的「無根本原因」案例，其實是調查不完整。

## 真實世界影響

來自除錯實例：
- 系統化方法：15–30 分鐘解決問題
- 隨機嘗試方法：2–3 小時的反覆嘗試
- 首次修復成功率：95% vs 40%
- 引入新錯誤的機率：接近零 vs 常見
