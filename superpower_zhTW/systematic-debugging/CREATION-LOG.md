# 建立紀錄：Systematic Debugging Skill

這是一個如何抽取、重組並補強關鍵 skill 的參考範例。

## 來源材料

從 `~/.claude/CLAUDE.md` 中抽取除錯框架：
- 四階段系統化流程（調查 → 模式分析 → 假說 → 實作）
- 核心要求：務必找出根本原因，絕不修復症狀
- 規則設計以抵抗時間壓力與合理化藉口

## 抽取決策

**納入的內容：**
- 完整的四階段框架及所有規則
- 反捷徑規定（「絕不修復症狀」、「停止並重新分析」）
- 抗壓語言（「即使更快也不行」、「即使我看起來在趕時間也不行」）
- 每個階段的具體步驟

**排除的內容：**
- 專案特定脈絡
- 相同規則的重複變體
- 敘述性說明（濃縮為原則）

## 依照 skill-creation/SKILL.md 的結構

1. **豐富的 when_to_use** — 包含症狀與反模式
2. **類型：技術** — 含步驟的具體流程
3. **關鍵字** — 「root cause」、「symptom」、「workaround」、「debugging」、「investigation」
4. **流程圖** — 「修復失敗」的決策點 → 重新分析 vs 繼續加修復
5. **逐階段細項** — 可掃讀的檢核清單格式
6. **反模式章節** — 說明不該做什麼（此 skill 的關鍵）

## 補強元素

框架設計以在壓力下抵抗合理化：

### 語言選擇
- 「ALWAYS」/「NEVER」（而非「should」/「try to」）
- 「even if faster」/「even if I seem in a hurry」
- 「STOP and re-analyze」（明確暫停）
- 「Don't skip past」（捕捉實際行為）

### 結構性防禦
- **第一階段為必要條件** — 無法跳到實作
- **單一假說規則** — 強制思考，防止散彈槍式修復
- **明確的失敗模式** — 「若第一次修復無效」附帶強制行動
- **反模式章節** — 清楚呈現捷徑的樣貌

### 冗餘設計
- 根本原因要求出現於概觀 + when_to_use + 第一階段 + 實作規則
- 「NEVER fix symptom」在不同脈絡出現四次
- 每個階段都有明確的「不得跳過」指引

## 測試方法

依照 skills/meta/testing-skills-with-subagents 建立四個驗證測試：

### 測試一：學術情境（無壓力）
- 簡單錯誤，無時間壓力
- **結果：** 完全合規，進行完整調查

### 測試二：時間壓力 + 明顯的快速修復
- 使用者「很趕」，症狀修復看起來很容易
- **結果：** 抵抗捷徑，遵循完整流程，找出真正的根本原因

### 測試三：複雜系統 + 不確定性
- 多層失敗，不確定是否能找到根本原因
- **結果：** 系統化調查，追蹤所有層級，找到來源

### 測試四：第一次修復失敗
- 假說無效，有再加入更多修復的誘惑
- **結果：** 停止、重新分析、形成新假說（無散彈槍）

**所有測試通過。** 未發現合理化藉口。

## 迭代

### 初始版本
- 完整的四階段框架
- 反模式章節
- 「修復失敗」決策的流程圖

### 強化一：TDD 參考
- 加入連結至 skills/testing/test-driven-development
- 附注說明 TDD 的「最簡程式碼」≠ 除錯的「根本原因」
- 防止方法論混淆

## 最終成果

補強完善的 skill：
- ✅ 清楚要求根本原因調查
- ✅ 抵抗時間壓力的合理化
- ✅ 提供每個階段的具體步驟
- ✅ 明確呈現反模式
- ✅ 在多種壓力情境下測試
- ✅ 釐清與 TDD 的關係
- ✅ 可投入使用

## 關鍵洞察

**最重要的補強：** 反模式章節呈現了當下感覺合理的確切捷徑。當 Claude 想到「我只要加這一個快速修復」時，看到那個確切的模式被列為錯誤，會產生認知摩擦。

## 使用範例

遇到錯誤時：
1. 載入 skill：skills/debugging/systematic-debugging
2. 閱讀概觀（10 秒）——重新確認要求
3. 遵循第一階段檢核清單——強制調查
4. 若想跳過——看到反模式，停止
5. 完成所有階段——找出根本原因

**時間投入：** 5–10 分鐘
**節省時間：** 數小時的症狀打地鼠
